## CRITICAL

### C1. Stored XSS через `|safe` на JSON с пользовательскими данными
- **Где:** `app/web/trade.py:315–327` (`top_items_json`, `top_clients_json`), `:986` (`items_json`, `ensure_ascii=False`); шаблоны `app/templates/trade/dashboard.html:217–225`, `app/templates/trade/rmk.html:109`.
- **Проблема:** `json.dumps` не экранирует `<`, `>`, `&`, `/`. Наименования номенклатуры/контрагентов (пользовательский ввод) выводятся через `{{ … | safe }}` внутрь `<script>`. Значение вида `</script><script>…</script>` разрывает script-контекст → исполняемый XSS на всех операторах (и в `rmk` дополнительно `ensure_ascii=False` — raw Unicode).
- **Исправление:** использовать Jinja-фильтр `|tojson` (экранирует `<` как `\u003c`), либо выводить в `<script type="application/json">` и читать через `JSON.parse`, с обязательным экранированием `</`.

### C2. Race condition при списании остатков (перепродажа / отрицательный остаток)
- **Где:** `app/services/stock_service.py:99–156` (`consume_batches`), `:220–240` (`reserve`); `app/services/document_service.py:314–330` (`_check_stock`).
- **Проблема:** чтение партий и уменьшение `batch.quantity` происходит без `SELECT … FOR UPDATE` (во всём проекте нет ни одного `with_for_update()`). Два параллельных `RASHOD` одновременно проходят проверку остатка и оба списывают → уход в минус / перепродажа.
- **Исправление:** `select(StockBatch).with_for_update()` в `consume_batches`, либо advisory-lock на (номенклатура, склад) на время проведения; аналогично для `reserve`.

### C3. Двойное проведение документа (неатомарная проверка статуса)
- **Где:** `app/services/document_service.py:277–311` (`post_document`), `:279–280`.
- **Проблема:** проверка `status == POSTED` идёт по in-memory объекту, атомарного перехода статуса в БД нет. Два конкурентных вызова `post_document` создают дублирующиеся движения.
- **Исправление:** атомарная смена статуса (`UPDATE … WHERE status != 'posted'` с проверкой числа затронутых строк) или advisory-lock на id документа на время проведения.

### C4. Себестоимость продажи (проводка 90.2/41) не формируется из-за `autoflush=False`
- **Где:** `app/services/document_service.py:566–577` (`_apply_accounting`, `RASHOD`); `app/core/database.py:27–32` (`autoflush=False`).
- **Проблема:** для `RASHOD` расходные `StockMovement` добавляются через `register_outgoing` без `flush()`. `_apply_accounting` затем выполняет `select(sum(StockMovement.amount))` по этому же документу. При `autoflush=False` SELECT не видит незакоммиченные строки → `cost == 0` → `entry("90.2","41", 0)` пропускается. Себестоимость в проводках продажи отсутствует.
- **Почему тесты зелёные:** `tests/conftest.py:33–35` пересоздаёт sessionmaker **без** `autoflush=False`, т.е. в тестах autoflush=True и стоимость считается, а в проде — нет. Расхождение тест/прод.
- **Исправление:** явный `await session.flush()` перед расчётом себестоимости (или вычислять стоимость из результата `consume_batches`, не перечитывая БД); привести тестовую фабрику к прод-настройкам.

## HIGH

### H1. Веб-слой не проверяет права доступа
- **Где:** `app/web/trade.py` — все GET-роуты (dashboard, catalog_*, zakazy_list, documents_journal, document_detail, reports_*), а также POST `rmk_shift_open` (:992), `rmk_shift_close` (:1010), `rmk_sell` (:1022), `inventarizaciya_submit` (:1336).
- **Проблема:** `_deny`/проверка прав вызывается только в части POST; права `catalog.read`, `documents.read`, `reports.read`, `documents.write/post` в web-слое не применяются. Любой аутентифицированный пользователь (в т.ч. бухгалтер без `documents.write` или пользователь без роли) может просматривать всё и создавать/проводить продажи, смены, инвентаризации через формы.
- **Исправление:** единый guard через `require_permission` (как в `app/api/*`) на всех web-роутах; `_deny` вернуть 403 (а не 303).

### H2. Пробел прав на чтение в REST API документов и в чатах
- **Где:** `app/api/documents.py:25–56` (`list_documents`, `get_document` — только `get_current_user`, без `documents.read`); `app/api/messaging.py:29–101` (только аутентификация, без прав и без проверки принадлежности чата).
- **Проблема:** пользователь без права `documents.read` читает все документы; любой аутентифицированный читает/пишет в любые чаты (IDOR).
- **Исправление:** `Depends(require_permission("documents.read"))`; для чатов — проверка прав и принадлежности чата пользователю/роли.

### H3. Нет rate limiting на вход/регистрацию/чат
- **Где:** `app/api/auth.py:17`, `app/customer/api.py` (`/api/login` :73, `/api/register` :62, `/api/chat` :198), `app/customer/web.py`, `app/web/auth.py:32`.
- **Проблема:** брутфорс паролей (в т.ч. слабых, мин. 4 символа у сотрудников / 6 у покупателей) и спам в чат ничем не ограничены.
- **Исправление:** rate limiter (`slowapi`/`fastapi-limiter`) по ключу IP+login/телефон; после N неудач — backoff/блокировка.

### H4. Слабые секреты по умолчанию, которые не блокируют запуск
- **Где:** `docker-compose.yml:6,25–26`, `.env.example:7,11`, `app/core/config.py:31–35`, `app/core/security.py:33–53`.
- **Проблема:** `ADMIN_PASSWORD=admin`, `SECRET_KEY=change-me…`, `POSTGRES_PASSWORD=uwu` — дефолты. `validate_security_settings()` только логирует warning, не останавливает запуск.
- **Исправление:** fail-fast в проде (нет `SECRET_KEY`/слабый пароль → отказ при `env=production`), обязательные переменные без дефолтов, генерация секрета при развёртывании.

### H5. Отсутствие CSRF-защиты при cookie-авторизации
- **Где:** `app/web/auth.py:50` (cookie `access_token`), все state-changing POST в `app/web/trade.py`, `app/web/admin.py`; `logout` через GET (`:54`).
- **Проблема:** авторизация по cookie (httponly, `samesite="lax"`) без CSRF-токена; `SameSite=Lax` лишь частично гасит cross-site POST (субдомены, старые браузеры), `logout` по GET — state-changing.
- **Исправление:** CSRF-токен (double-submit cookie) на все POST; `logout` перевести на POST.

### H6. Replay-атака на initData мессенджеров
- **Где:** `app/services/miniapp_service.py:40–79` (`validate_init_data`).
- **Проблема:** HMAC-подпись проверяется корректно, но `auth_date` (Telegram) / `vk_ts` (MAX) не извлекаются и не проверяются на свежесть. Перехваченный валидный `initData` переигрывается бесконечно.
- **Исправление:** проверять `auth_date`/`vk_ts` против текущего времени (допуск 1–5 мин).

### H7. `miniapp_dev` — полный обход аутентификации
- **Где:** `app/customer/miniapp.py:34–42`, `app/core/config.py:50`.
- **Проблема:** при `MINIAPP_DEV=true` подпись не проверяется, `external_id` и `channel` берутся из query-параметров без валидации → любой получает customer-токен с авто-созданием учётки.
- **Исправление:** запретить в проде (проверка на старте), dev-режим ограничить (`debug=True` + allowlist), `channel` валидировать по белому списку.

### H8. Режимы контроля остатков сломаны
- **Где:** `app/services/document_service.py:291–330`, `app/services/stock_service.py:99–156`.
- **Проблема:**
  - «Без контроля» (`RestockControl.NONE`) не работает: `_check_stock` пропускается, но `consume_batches` всегда кидает `InsufficientStockError` (stock_service.py:126) — отрицательные остатки невозможны даже при отключённом контроле.
  - «По фирме» (`BY_FIRM`) проверяет остаток агрегированно по всем складам (`sklad_id=None`), а списание идёт строго по складу строки — контроль не соответствует фактическому списанию.
- **Исправление:** при `NONE` разрешить списание в минус (или отложенное), при `BY_FIRM` списывать по сумме фирмы, согласовав проверку и списание.

### H9. Наличные накладные не создают денежных движений
- **Где:** `app/services/document_service.py:455–540` (`_apply_money_and_settlement`).
- **Проблема:** `RASHOD`/`PRIHOD` с `subtype == CASH` не формируют `MoneyMovement` — касса не пополняется/не уменьшается при продаже/покупке за наличные.
- **Исправление:** добавить генерацию `MoneyMovement` для наличных накладных.

### H10. Отмена проведения ломает себестоимость и даёт отрицательные остатки
- **Где:** `app/services/document_service.py:618–661` (`_rollback_stock`).
- **Проблема:**
  - Для расходов/перемещений создаётся **новая** партия с усреднённой себестоимостью вместо восстановления исходных партий → после unpost/repost себестоимость искажается (FIFO/LIFO ломаются).
  - Для прихода: `batch.quantity -= movement.quantity`; если партия уже частично израсходована поздним расходом, остаток уходит в минус.
- **Исправление:** восстанавливать исходные партии по ссылкам движений (хранить состав списания), контролировать порядок unpost (обратный хронологический) и запрещать unpost при израсходованной партии.

### H11. Нет атомарного отката при ошибке проведения
- **Где:** `app/services/document_service.py:277–311`, `app/core/database.py:39–42`.
- **Проблема:** при исключении внутри `post_document` нет явного `session.rollback()`; сессия остаётся «грязной» до закрытия. Частичные изменения зависят от неявного rollback на `close()`, что хрупко и неочевидно.
- **Исправление:** обернуть проведение в явную транзакцию `try/except` + `rollback()`, единый `commit` в конце.

### H12. Гонка нумерации справочников
- **Где:** `app/services/catalog_service.py:58–72` (`next_code`).
- **Проблема:** `SELECT max(code)` затем INSERT без advisory-lock → два параллельных создания дают одинаковый код → нарушение unique-констрейнта (500).
- **Исправление:** применить тот же advisory-lock, что и для документов (`next_document_number`), либо `INSERT … ON CONFLICT` + повтор.

## MEDIUM

### M1. Cookie без флага `secure`
- **Где:** `app/web/auth.py:50`, `app/customer/web.py:48`, `app/customer/miniapp.py:60–65`.
- **Проблема:** `set_cookie(…, httponly=True, samesite="lax")` без `secure=True` — за HTTPS токен может уйти по HTTP.
- **Исправление:** добавить `secure=True` (с учётом прокси), явный `max_age`.

### M2. Отчёты: массовые N+1 и отсутствие пагинации
- **Где:** `app/services/report_service.py` (построчные `session.get` в `stock_balances:54–55`, `stock_movements:87–89`, `sales_report:120–125`, `settlement_balances`, `money_movements`, `turnover_statement` и др.); все отчёты без `limit/offset`.
- **Проблема:** деградация на больших объёмах; полная выгрузка в память.
- **Исправление:** `selectinload`/JOIN-агрегация, себестоимость по документам одним `GROUP BY`, пагинация + cap на период.

### M3. Ошибки расчётов в отчётах
- **Где:** `app/services/report_service.py`.
- **Проблемы:**
  - `commission_report:317–328` — долг комитентам не уменьшается на оплаты (join по `document_id`, а оплаты имеют `document_id` платёжки).
  - `stock_balances:44–67` — резерв вычитается из всех видов собственности, а не только `own`.
  - `cash_book:399–424` — нет входящего остатка до `start`.
  - `abc_analysis:245–255` — граничная позиция классифицируется в младший класс.
  - отчёты по деньгам/взаиморасчётам суммируют разные валюты и фирмы.
- **Исправление:** см. комментарии выше; добавить группировку/фильтр по фирме и валюте.

### M4. Изоляция по фирме (multi-tenancy) отсутствует
- **Где:** все `list_all`/`get_document`/отчёты без фильтра по `Firma`.
- **Проблема:** пользователь видит данные всех юрлиц; модели движений (`MoneyMovement`/`SettlementMovement`) вообще не имеют `firma_id`/`valyuta_id`.
- **Исправление:** добавить фирму/валюту в модели движений и scoping в запросах (или явно зафиксировать «одна база — одна фирма»).

### M5. Checkout покупателя: нет проверки остатков, нет rollback, нет НДС
- **Где:** `app/services/customer_service.py:264–310`.
- **Проблемы:** корзина очищается до создания документа без атомарной транзакции/rollback; остаток не сверяется; `nds_rate_id` не передаётся → `nds_total=0`.
- **Исправление:** транзакция с `rollback`, проверка остатков, передача `nds_rate_id` и явное соглашение «цена с/без НДС».

### M6. Связывание контрагента по подстроке телефона
- **Где:** `app/services/customer_service.py:247–261` (`match_kontragent_by_phone`).
- **Проблема:** `Kontragent.phones.ilike(f"%{phone}%")` — короткий номер совпадает с чужим, `%`/`_` не экранируются → заказ привязывается к чужому контрагенту.
- **Исправление:** точное совпадение нормализованного телефона, экранирование wildcard.

### M7. Валидация входных данных отсутствует/слабая
- **Где:** web-формы `app/web/trade.py` (создание справочников, `_parse_items`, `rmk_sell`), `app/services/customer_service.py` (телефон только по длине), `app/schemas/*`.
- **Проблемы:** произвольные строки `vid`/`tip` (без проверки enum), нет ограничений длины `name`/`inn`, отрицательные/нулевые количество и цена, `nomenklatura_id` не проверяется на существование (→ IntegrityError/500), телефон «abc» принимается.
- **Исправление:** валидация enum, max-length, `quantity > 0`, `price >= 0`, проверка существования ссылок, нормализация телефона (E.164/регэксп).

### M8. Частичный коммит в `update_valyuta`
- **Где:** `app/web/trade.py:776–784`.
- **Проблема:** `commit` для `code`/`name` выполняется до `set_rate`; при ошибке установки курса наименование/код уже сохранены — рассинхрон.
- **Исправление:** один `commit` в конце.

### M9. Обход блокировки редактирования проведённого документа
- **Где:** `app/web/trade.py:1570–1586` (`document_edit_submit`) против GET-формы `:1548–1567`.
- **Проблема:** POST-обработчик не перепроверяет `status == "posted"` → прямой POST меняет позиции проведённого документа без распроведения.
- **Исправление:** проверять статус в POST и отклонять.

### M10. `allow_future_dates` не enforced
- **Где:** `app/web/trade.py:1461–1509`, `:1147–1175`; константа управляется в `admin.py:188`.
- **Проблема:** константа заведена, но дата документа не проверяется на будущность.
- **Исправление:** при `doc_date > today` и `allow_future_dates=False` отклонять.

### M11. Загрузка изображений без лимита и проверки содержимого
- **Где:** `app/web/trade.py:661–705` (`upload_nomenklatura_image`).
- **Проблема:** весь файл читается в память (`file.read()`), тип проверяется только по `content_type` (клиентский), magic-байты не проверяются → memory-DoS, спуфинг.
- **Исправление:** лимит размера (чтение потоком), проверка сигнатур (Pillow).

### M12. Валютная переоценка объявлена, но не реализована
- **Где:** `app/models/enums.py:109` (`PEREOCENKA`), `app/services/document_service.py` (нет логики проведения переоценки).
- **Проблема:** `DocType.PEREOCENKA` есть, но проведение/курсовые разницы не реализованы; противоречит ТЗ («двойная валютная оценка», «переоценка валюты»).
- **Исправление:** реализовать переоценку либо убрать/пометить как roadmap.

### M13. Неполные бухгалтерские проводки
- **Где:** `app/services/document_service.py:543–586` (`_apply_accounting`).
- **Проблема:** проводки формируются только для PRIHOD/VOZVRAT/RASHOD/ПКО/РКО/платёжное поручение; для SPISANIE, OPRIHODOVANIE, INVENTARIZACIYA, PEREMESHENIE, VVOD_OSTATKOV, PEREOCENKA — нет. `nomenklatura_id` в `AccountingEntry` не заполняется.
- **Исправление:** дополнить проводки по видам документов и заполнять аналитику.

### M14. Аудит: `_log` пишет `created_by_id`, а не действующего пользователя; справочники не логируются
- **Где:** `app/services/document_service.py:42–51`; `app/web/trade.py` (все `create_*`/`update_*`).
- **Проблема:** `AuditLog.user_id = document.created_by_id`, а не пользователь, выполнивший действие; мутации справочников/кассовых смен/статуса заявки не журналируются.
- **Исправление:** передавать действующего пользователя в `_log`, добавить AuditLog для catalog CRUD и смен.

### M15. Утечки asyncio-задач ботов
- **Где:** `app/bots/service.py:51–65` (`start`/`stop_all`).
- **Проблема:** `stop_all` делает `cancel()` без `await gather`; `start` перезаписывает задачу канала без отмены старой → дублирование polling и «Task was destroyed but it is pending».
- **Исправление:** `await asyncio.gather(*tasks, return_exceptions=True)`; отменять старую задачу перед перезапуском.

### M16. Гонки в регистрации покупателя и привязке
- **Где:** `app/services/customer_service.py:62–70` (`register`), `app/models/customer.py` (`CustomerBinding` без unique на `channel+external_id`), `app/services/miniapp_service.py:116–137`.
- **Проблема:** проверка→insert неатомарна (IntegrityError/500); нет unique-констрейнта → `MultipleResultsFound`.
- **Исправление:** `UniqueConstraint(channel, external_id)`, обработка `IntegrityError` → 409.

### M17. `/healthz` не проверяет БД
