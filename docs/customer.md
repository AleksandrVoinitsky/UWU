# Клиентский сайт покупателя (отдельная ветвь процесса)

## Назначение

Отдельный сайт/домен для внешних клиентов, где покупатель может
зарегистрироваться, просмотреть каталог товаров в наличии, собрать корзину и
оформить заказ. Заказ попадает в торговый учёт как «Заявка покупателя»
(`ZAKAZ`), которую оператор ведёт обычным циклом (резерв → отгрузка).

Учётные записи покупателей полностью отделены от сотрудников — другая таблица
и отдельные токены, пересечение исключено.

## Архитектура

Клиентское приложение — отдельный FastAPI-апп в [`app/customer/`](app/customer/),
монтируется в основное приложение по пути `/shop` (в одном контейнере); на
отдельный домен выносится реверс-прокси (nginx/traefik). Переиспользует ядро:
модели, сервисы, БД.

- [`app/customer/api.py`](app/customer/api.py) — REST API (переиспользуется
  сайтом и MiniApp).
- [`app/customer/web.py`](app/customer/web.py) — серверные страницы.
- [`app/services/customer_service.py`](app/services/customer_service.py) —
  бизнес-логика (регистрация, корзина, заказ, привязка к контрагенту).
- [`app/services/pdf_service.py`](app/services/pdf_service.py) — PDF заказа (WeasyPrint).

## Модели данных

- [`app/models/customer.py`](app/models/customer.py): `Customer` (телефон —
  логин, `password_hash`, `name`, `is_active`), `Cart` (одна на покупателя),
  `CartItem` (позиция).
- [`app/models/catalog/category.py`](app/models/catalog/category.py): `Category`
  (иерархические категории товаров); `Nomenklatura.category_id` — привязка.

Миграция: `alembic/versions/b2c3d4e5f6a7_customer.py`.

## Безопасность (разделение аккаунтов)

Токены сотрудников и покупателей различаются claim'ом `type`:

- `type="user"` — сотрудник (`create_access_token` / `decode_access_token`).
- `type="customer"` — покупатель (`create_customer_token` / `decode_customer_token`).

Токен покупателя не проходит проверку как сотрудник и наоборот (см.
[`app/core/security.py`](app/core/security.py)).

## Цикл покупателя

1. **Регистрация/вход** — телефон + пароль ×2 (+ имя). SMS-код — позже (заглушка).
2. **Каталог** — карточки товаров (фото, название, описание, цена) с фильтром по
   категориям и поиском; показываются только позиции **в наличии**.
3. **Корзина** — серверная, в БД (общая для сайта и MiniApp).
4. **Подтверждение** — создаёт `ZAKAZ` (`extra.source="customer"`,
   `extra.customer_phone`), корзина очищается.
5. **PDF** — скачивание печатной формы заказа.

## Привязка к контрагентам

При подтверждении заказа номер телефона покупателя ищется среди контрагентов
(точное совпадение поля `phones`, затем подстрока). Если найден — заявка явно
привязывается к контрагенту (`kontragent_id`); иначе телефон остаётся виден в
`extra.customer_phone`, а привязка выполняется оператором вручную.

## Администрирование

- `/admin/customers` — список, просмотр профиля (с заказами), удаление.
- `/catalog/categories` — справочник категорий (создание/удаление).
- Поле «Категория» в форме номенклатуры (создание/редактирование).

## MiniApp (следующая итерация)

Вся логика покупателя вынесена в REST API `/shop/api/*`, поэтому MiniApp
Telegram/MAX — это тонкая оболочка над тем же API (entry-точка под webview
мессенджера + авторизация через initData). Архитектура уже готова к
переиспользованию.

## Тесты

[`tests/test_customer.py`](tests/test_customer.py) покрывает: разделение токенов,
регистрацию/вход (в т.ч. дубли телефона и неверный пароль), каталог «в наличии»,
категории, корзину, оформление заказа (создание `ZAKAZ`, очистка корзины),
привязку к контрагенту по телефону, HTML печатной формы.

## PDF

PDF генерируется WeasyPrint (HTML → PDF, шаблон
[`app/templates/customer/order_pdf.html`](app/templates/customer/order_pdf.html)).
WeasyPrint импортируется лениво — на платформах без системных библиотек (GTK)
сам сервис остаётся импортируемым; PDF работает в Docker (Linux), где в образе
установлены `libpango`, `libpangoft2`, `libharfbuzz` и шрифты DejaVu.
