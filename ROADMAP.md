# Планы развития (Roadmap)

> Заметка о будущих направлениях. Не является ТЗ — фиксирует принятые решения,
> чтобы при возврате к задаче не переобсуждать архитектуру заново.

## AI-агент (следующий крупный этап)

### Решение по размещению

AI-агент — **отдельный репозиторий и отдельный контейнер** (хостинг рассчитан
на модель «1 репозиторий = 1 контейнер»). Текущий сервис UWU (`app/`) остаётся
ядром учёта и единственным источником бизнес-логики и данных.

### Почему отдельно

- Разный жизненный цикл: LLM-вызовы медленные/потоковые, с ретраями и паузами
  «человек подтверждает» — не должны блокировать транзакционное ядро.
- Независимые деплой и масштабирование: правки промптов/тулзов не требуют
  пересборки учётного сервиса.
- Изоляция секретов и LLM-поверхности (промпт-инъекции из чатов).
- Ядро уже — чистый headless-бэкенд с REST API и правами: агент является
  *клиентом* API, а не внедряется в учётную логику.

### Технологии

- **Оркестрация — LangGraph**: state machine + checkpointer + interrupts
  (human-in-the-loop) + tools. Привязка к конкретному LLM-провайдеру — отдельно.
- **Аутентификация — API-ключ** агента (дополнить аутентификацию в ядре, сейчас
  только JWT), маппится на роль агента с урезанными правами.
- **Тулзы — тонкие обёртки над REST API ядра** (не прямой доступ к БД), чтобы не
  было дрейфа бизнес-логики между агентом и интерфейсом.

### Объём (функции агента)

- Знает остатки и справочник (названия товаров, цены, наличие).
- Обрабатывает заявки покупателей (создание/резервирование/статусы).
- Может предлагать продажу, но **проведение — под присмотром человека**
  (агент создаёт документ как `DRAFT`, человек одобряет → `post`).
- Работает на всех этапах: помощник внутри программы + общение в мессенджерах
  и чатах.

### Точки интеграции с ядром

- Каналы сообщений уже есть: `app/bots/` + `app/models/messaging.py`
  (`internal | telegram | maks | site`), `deliver_outgoing`, роутинг входящих.
  Агент — ещё один потребитель/производитель этого слоя.
- Human-in-the-loop = существующая связка `DRAFT → post_document`.
- Права — существующая модель (`require_permission`, `PERMISSIONS`); добавить
  роль/принципала агента.

### Что добавить в ядро (минимально)

1. API-key аутентификация (таблица ключей, зависимость рядом с `get_current_user`).
2. Роль агента с ограниченным набором прав (читать остатки/каталог, черновики,
   заявки; без `documents.post` без эскалации).
3. По необходимости — компактные tool-friendly эндпоинты
   (`search_nomenklatura`, `get_stock`, `get_zakaz`).

### Открытые вопросы (уточнить перед реализацией)

- Строгость надзора: каждую продажу подтверждает человек или только выше порога.
- Хранилище состояния агента (checkpointer): PostgreSQL (отдельная схема) или Redis.
- Порядок подключения каналов (Telegram / MAX / site-чат).
- Провайдер модели и нужен ли стриминг ответов в чат.
